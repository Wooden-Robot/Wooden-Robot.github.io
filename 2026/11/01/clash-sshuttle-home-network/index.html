一台 VPS，既能科学上网，也能访问家里的 NAS

发表于 2026-11-01 分类于 网络折腾 阅读次数： Disqus：
本文字数： 8.6k 阅读时长 ≈ 8 分钟
不想给每台设备配置 SSH？让原来用于科学上网的 VPS 运行 sshuttle，再给 Clash 加一条规则，就能把访问家里内网的请求交给这台 VPS。本文从一台 NAS 的访问过程讲起，一步步完成配置。

我想解决的事情其实很简单：人在外面，也能打开家里的 NAS。

但我不太想为了这件事，再给电脑、手机和平板分别配置一套 SSH 连接，更不想把 SSH 私钥到处复制。

既然这些设备平时已经在用 Clash，背后也有一台自己的科学上网 VPS，那就换个思路：让这台 VPS 顺便帮我访问家里的设备。

手机和电脑继续用原来的节点。新增的工作放到 VPS 上，客户端只需要告诉 Clash：访问家里这些 IP 时，也交给这台 VPS。

先说清楚：不是让手机直接 SSH 回家

假设家里的 NAS 地址是 192.168.123.10，管理页面用的是 5000 端口。

到了外面，这个地址并不会自动指向我家里的 NAS。现在要做的，就是给这次访问安排一条能回家的路：

Clash 和 sshuttle 不在同一台机器上。Clash 在手机、电脑上；sshuttle 在那台科学上网 VPS 上。

这里没有新增一个“SSH 节点”，也没有额外开一个 SOCKS5 服务。客户端仍然使用原来的 VLESS Reality 等代理节点；只是 VPS 收到访问家里 IP 的请求后，再由 sshuttle 把连接送回家。1

可以把它理解为：以前 VPS 只帮我访问外网，现在多接了一份“访问家里设备”的活。

开始前，先确认这几件事

本文不是从零搭建科学上网服务。它假设你已经有一台自己能管理的 Linux VPS，Clash 也已经能通过这台服务器正常上网。

另外，VPS 必须能通过 SSH 连上一台“能访问家里内网”的设备。这台设备可以是 NAS、Linux 主机，或者具备相应环境的路由器；它需要能运行兼容的 Python。2

如果 VPS 连家里的 SSH 都连不上，就先解决这一步。sshuttle 不能在没有任何可用连接的情况下，凭空打通家里的网络。

本文还默认 Xray 和 sshuttle 直接运行在同一台 VPS 的系统里。如果 Xray 装在 Docker 容器中，先留意文末的容器提醒，不要把“同一台服务器”当成“网络一定一样”。

断了怎么办？ SSH 长时间收不到回复时，会通过心跳判断失联；进程退出后，systemd 等 10 秒再启动。这里的 30 秒和 3 次，对应典型情况下约 90 秒发现失联，不是保证 90 秒就一定恢复。3 5

为什么要放前面，为什么不能写 DIRECT？

因为不少配置会把内网地址直接设为 DIRECT，也就是让当前这台手机或电脑自己连接。

人在外面时，让手机自己访问 192.168.123.10，并不能找到家里的 NAS。我们需要的是：先交给 VPS，再让 VPS 帮忙回家。

Mihomo 的普通规则从上往下匹配，所以这条“回家规则”要放在宽泛的私网直连规则之前。9

还有一点：别把目标写成会在不同服务器之间切换的“自动选择”组。只有安装了 sshuttle、能连回家的那台 VPS 才认识这条路。内网访问应固定走它，日常外网仍然可以继续用原来的自动选择。

节点没选错，VPS 自己也能访问，但手机还是打不开

接下来检查 VPS 上的 Xray。

VPS 能访问家里，不代表它允许所有代理客户端也访问家里。 这是两回事。

例如，服务端配置可能把私网地址拦住；当前 Xray 官方文档也说明，Freedom 出站对 VLESS 等入站默认有私有和保留地址访问限制，需要按需明确放行。12

不要因此把所有保护都关闭。只允许需要访问的设备和端口就好，例如 NAS 的 192.168.123.10:5000。文末有对应示例，但必须先确认你的 Xray 版本支持相关字段。

有几个边界，提前知道能少绕路

别用 ping 作为唯一的判断标准。 本文用的是 TCP 服务测试。sshuttle 常用的 NAT / nft 方式不提供完整的 ICMP、普通 UDP 和广播转发，所以“网页能开但 ping 不通”不矛盾，也别期待 NAS 一定自动出现在局域网设备列表里。2

外面的网络最好不要和家里用同一段地址。 两边都叫 192.168.123.* 时，同一个 IP 到底指向哪边就容易混淆。优先把其中一边换成不同网段，尤其不要直接照搬 TUN 配置去覆盖当前网络的网关地址。

Xray 装在 Docker 里要单独检查。 Docker bridge 模式可以理解为“容器自己还有一层网络”，不是宿主机上测试成功，容器就一定成功。本文没有配置容器流量接入 sshuttle；这种部署需另外验证和调整。不要为了试错就清空防火墙，或直接改动正在使用的容器网络模式。13

SSH 私钥少放几份，是方便管理，不是从此没有风险。 一旦某人拿到有内网权限的代理账户，他仍可能通过 VPS 访问已放行的设备。只放行必要的地址和端口，NAS 自身也要保留可靠的登录认证。VPS 是这条路的中间站，同样需要保护。12

还有，自动重连只负责重新建立通路，不保证原来的下载、网页会话不断。连接中断后，应用可能仍需刷新或重试。

最后，把它记成一句话就够了

客户端还是原来的 Clash，节点还是原来的 VPS；只是在 VPS 上加一个 sshuttle，让它多一条回家的路。

访问外网，照旧。访问家里的地址，先交给指定 VPS，再由它送回家。

我更喜欢这种分工：需要长期保持的 SSH 连接集中在 VPS，手机和电脑不再各自维护一套。换设备时，也不用再琢磨 SSH 私钥该怎么复制、放在哪里。

不是又搭了一套更复杂的系统，而是让已经在用的那台服务器，多做一件有用的事。
