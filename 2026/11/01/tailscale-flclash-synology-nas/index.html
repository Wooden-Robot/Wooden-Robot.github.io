不用公网 IP，也能通过域名访问群晖 NAS：Tailscale + FlClash 实战教程

发表于 2026-11-01 分类于 技术教程 ， 网络与 NAS 阅读次数： Disqus：
本文字数： 6k 阅读时长 ≈ 5 分钟
使用群晖 Tailscale 子网路由与 FlClash 内置 Tailscale 出站，实现通过 HTTPS 域名安全访问家庭 NAS，并排查 Fake-IP、SERVFAIL 和内核 Hosts 问题。

家里的群晖 NAS 上运行着 DSM、Docker、影音和其他自建服务。在局域网中访问很方便，但外出后如何继续用同一个 HTTPS 域名访问这些服务，而且不暴露公网端口？

我最终采用的方案是：群晖通过 Tailscale 发布家庭子网路由；FlClash 使用 Mihomo 内置的 type: tailscale 节点，按规则把家庭内网请求送进 Tailscale。 实际部署中还踩到了「IP 能访问、域名却报 SERVFAIL」的坑，最后通过 Mihomo 内核 Hosts 解决。

一、方案与网络拓扑

本文的示例环境如下（均为演示地址，按自己的环境替换）：

项目 示例值
家庭局域网网段 192.168.123.0/24
群晖 NAS 局域网 IP 192.168.123.163
NAS 访问域名 nas.example.com
群晖 HTTPS 反向代理端口 443
FlClash 家庭网络策略组 Home

最终实现的链路：

与普通的「通过公网 IP + DDNS + 端口映射」方案相比，这套方案不需要把 NAS 的业务端口暴露在公网，也不要求家里有可入站的公网 IP。

两者分工很明确：Tailscale 负责组网和访问家庭子网，Mihomo 负责流量分流。

配置项 示例

不同服务需换成其对应的后端地址及端口。如果使用了 HTTPS 后端自签证书，还要考虑反向代理的证书验证设置。

为 nas.example.com 绑定有效的 TLS 证书；不开放公网 80/443 的情况下，可使用 DNS-01 验证签发或续期证书。

为什么 IP 直连 443 可能不工作？ 因为浏览器使用域名访问时，会在 TLS 握手中提供 SNI，并在 HTTP 中发送 Host；反向代理可能依靠这些信息选择服务。因此，https://192.168.123.163 和 https://nas.example.com 不一定等价。

1. 生成 Auth Key

登录 Tailscale Keys，生成用于首次注册的 Auth Key。

五、排障：IP 能访问，域名却打不开

  • 独立 Tailscale 客户端访问域名正常；
  • FlClash 的 SSH 出站访问同一个域名正常；
  • 但 FlClash 内置 type: tailscale 访问该域名时，会出现超时、TLS 握手中断或 SERVFAIL。

备选方案：Tailscale Split DNS

Tailscale 管理后台也支持配置域名专用 DNS：

https://login.tailscale.com/admin/dns

可以在 Nameservers 中添加 Custom DNS，并限定到 example.com，前提是该 DNS 服务器确实能够解析出正确的家庭私有 IP。

不过，Tailscale 的 DNS 设置属于 Tailnet 级别，可能影响其他启用了「Use Tailscale DNS settings」的客户端；在同时运行独立 Tailscale 和其他 TUN 代理时还可能遇到 DNS/路由冲突。

因此，对于仅访问少量家庭域名的场景，我更推荐在 FlClash 的内核 Hosts 中管理映射。

七、Mac 和 Android 的使用区别

Android：主要使用 FlClash 内置 Tailscale

Android 端的 FlClash 通常通过系统 VPN 接口接管流量。配置 TS-HOME 后，直接让相应规则选择 Home 即可，无须再同时运行另一套独立 Tailscale VPN。

Mac：两种方式任选其一

方案 A：FlClash TUN 开启，独立 Tailscale 关闭。

这是本文实际采用的整合方式：

  • FlClash 接管目标应用的网络流量；
  • 访问家庭内网的请求走 TS-HOME；
  • 普通互联网继续按原有规则分流。

方案 B：独立 Tailscale 开启，FlClash TUN 关闭，使用系统代理。

此时独立 Tailscale 负责系统路由。对已经可以通过 macOS 路由到达的家庭 IP，FlClash 规则可以视情况选择 DIRECT，由系统送入独立 Tailscale。但这种方式可能受到 macOS 的代理绕过列表影响。

不建议在没有规划的情况下，让两套 TUN/VPN 同时修改重叠网段的路由和 DNS。

八、常见问题速查

现象 排查方向
Tailscale 节点无法登录 Auth Key、节点状态、Tailnet 设备列表
Duplicate node key 是否跨设备复制了已注册的状态目录
家庭内网 IP 不通 accept-routes、子网路由批准、ACL、防火墙
IP 通但域名不通 内核 Hosts、DNS、出站拨号错误日志
DNS 返回 198.18.x.x 可能是正常 Fake-IP，结合实际连接判断
出现 SERVFAIL 区分 Mihomo DNS 和 Tailscale 内部解析器
HTTPS 报证书错误或返回错误站点 检查 SNI、Host、反向代理和证书
Mac 访问内网不正常 TUN、系统代理绕过列表和策略组选择
换设备后无法连接 重新注册节点，避免共用状态目录

额外建议：为群晖在路由器上设置 DHCP 地址保留，避免 IP 变化导致内核 Hosts 失效；为 Tailnet 设置适当的访问权限；不要在公开仓库提交真实 Auth Key、节点认证信息或完整代理配置。

九、总结

最初以为，只要能从外网访问家庭内网 IP，就能自然地通过域名访问群晖。实际部署后才发现，组网、分流、DNS 和 HTTPS 反向代理是不同层次的问题。

这套方案最终只需要四个关键步骤：

  1. 群晖通过 Tailscale 发布 192.168.123.0/24 子网路由；
  2. FlClash 添加 type: tailscale 节点并开启 accept-routes；
  3. 使用 DOMAIN 和 IP-CIDR 将家庭内网流量指向 Home；
  4. 用 Mihomo 内核 Hosts 让 NAS 域名稳定解析到私有 IP。

最终，无论在 Android 还是 Mac 上，都可以通过统一的 HTTPS 域名访问家里的 NAS，而不必在路由器上对公网开放 NAS 的业务端口，也不必为了访问家庭网络频繁切换独立 VPN。
